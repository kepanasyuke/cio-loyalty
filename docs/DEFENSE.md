# Как презентовать проект под вакансию

Документ для отклика на вакансию PHP-разработчика в ООО «ЦИО». Здесь — короткий питч, привязка проекта к пунктам
вакансии, сценарий демо и ответы на вопросы, которые задают на техническом интервью.

## 1. Питч на минуту

> Сделал backend сервиса лояльности для брендов — как продукт digital-агентства: одно ядро, несколько брендов,
> мобильное REST API и админка для операторов.
>
> Внутри — Laravel 12 на PHP 8.3, мультитенантность через контекст бренда, журнал баллов с блокировками и
> идемпотентностью, каталог наград с кешем в Redis, оплата пакетов баллов через шлюз с вебхуком и защитой от
> повторной доставки, очереди на пуши и расписание для сгорания баллов.
>
> Всё, что критично для денег и баллов, закрыто feature-тестами: обмен, недостаток баллов, нулевой сток,
> чужой бренд, повторный запрос с тем же ключом, повторный вебхук.

## 3. Демо на 5 минут

1. `php artisan migrate --seed`, запуск `serve` и `queue:work`.
2. Админка `/admin/login` → дашборд: клиенты, активные награды, ожидающие выдачи, начислено за день.
3. Меняем награду (например, сток 20 → 2), показываем, что каталог в API сразу отдаёт новые данные (сброс кеша).
4. Через curl: OTP → токен → `/me` с балансом и уровнем → `/rewards`.
5. Обмен награды: баланс уменьшился, сток уменьшился, в админке появился код выдачи.
6. Повторяем тот же запрос с `Idempotency-Key` — второго списания нет.
7. Покупка пакета баллов и вебхук `payment.succeeded` → баллы начислены; повтор вебхука — не начислены.
8. `php artisan test` — зелёный прогон.

## 4. Вопросы, которые почти наверняка зададут

**Как избежали двойного списания при параллельных запросах?**
Блокировка строки счёта `SELECT ... FOR UPDATE` + единый порядок захвата (награда, затем счёт). Уникальный индекс
на `idempotency_key` ловит повторы, которые всё же проскочили на уровне транспорта.

**Почему баланс не считается как `SUM(points)`?**
Чтение баланса — самая частая операция в приложении; агрегат по журналу на каждом запросе дороже денормализации.
Журнал остаётся источником истины, баланс обновляется в той же транзакции и проверяется тестами.

**Что будет при сбое между списанием и выдачей кода?**
Обе записи в одной транзакции: либо есть и обмен, и транзакция баллов, либо нет ни одной. Push отправляется
после коммита (`afterCommit`), поэтому уведомление не уйдёт о несуществующем обмене.

**Как обеспечили изоляцию брендов?**
Заголовок `X-Brand` → `BrandContext` (scoped), `EnsureCustomerBrand` сверяет бренд токена с брендом запроса,
в админке область видимости задаётся ролью и дополнительно проверяется на уровне конкретной модели.

**Почему не GraphQL?**
Восемь эндпоинтов с фиксированными экранами — GraphQL добавил бы слой и сложность без выгоды. Если появятся
партнёрские интеграции с разными наборами полей, переход на Lighthouse обсуждаем и описан в плане.

**Что бы улучшили при росте нагрузки?**
Партиционирование журнала, Horizon вместо `queue:work`, read-реплика для отчётов админки, кеш каталога с
тегами, вынос начисления баллов в отдельный сервис при появлении офлайн-точек.

**Как тестировали платёжную интеграцию без боевых ключей?**
Контракт `PaymentGateway`: в тестах поднимается `fake`-драйвер, вебхук проверяется на фиктивных событиях,
реальный клиент ЮKassa покрыт кодом с таймаутами и обработкой ошибок шлюза.

## 5. Что сказать честно

Проект — пет-проект, не продакшн. В нём нет Horizon, GraphQL, Elasticsearch и боевого SMS-провайдера; в README и
`docs/ARCHITECTURE.md` это зафиксировано вместе с причиной и планом. Такая честность работает лучше, чем попытка
выдать демо за промышленную систему: видно, что решения принимались осознанно.

## 6. Что улучшить перед отправкой отклика (опционально)

- Записать 60-секундное видео демо и приложить ссылку в письме.
- Добавить `laravel/horizon` и скриншот дашборда очередей — закрывает пункт «плюсом».
- Прикрутить `SmsSender` с фейковым провайдером: симметрично платёжному шлюзу.
- Прогнать `vendor/bin/pint` и оставить один аккуратный коммит «initial».
